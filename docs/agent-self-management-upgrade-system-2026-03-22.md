## 1. 文档目标

本文用于定义“智能体自我管理升级系统”的设计边界、工具分层、运行方法与升级流程。

本系统的核心目标不是让智能体“无限自治”，而是让智能体能够围绕自己的身份、记忆、照片与提示词，进行可控、可审计、可持续的自我完善。

这套系统重点解决以下问题：

1. 智能体如何安全地修改“自己”的内容，而不是误用公共工具乱改。
2. 智能体如何基于长期记忆与阶段总结，持续优化自己，而不是每轮重新开始。
3. 智能体如何在不引入复杂“自我状态中心”的前提下，形成稳定的自我升级闭环。
4. 智能体如何区分“公共能力”与“自我能力”，避免提示词越来越脏、工具语义越来越混乱。

---

## 2. 核心设计结论

### 2.1 结论

1. “修改别人/修改通用对象”和“修改自己”必须分开设计。
2. 自我管理不应继续依赖公共工具上的软提示词约束，而应收敛为独立的 `my_*` 或 `self_*` 工具域。
3. 本阶段不引入单独的“自我状态中心（Self State Center）”。
4. 自我完善能力的主轴应建立在“记忆总结系统”上，而不是建立一套额外、重型、长期常驻的自治状态机。
5. 智能体的升级应遵循“总结 -> 形成变更建议 -> 请求确认或自动小修 -> 落盘 -> 记录原因”的闭环。

### 2.2 当前阶段不做

1. 不建设独立数据库形式的自我状态中心。
2. 不让智能体无确认地重写自己的核心身份。
3. 不让智能体通过公共 `file_write`、公共 `image_generate` 直接篡改自己的核心设定。
4. 不做复杂自治人格漂移、自动世界观重构、自动关系改写。

---

## 3. 总体设计原则

### 3.1 自我管理与公共能力分离

公共工具继续负责通用任务：

1. `image_generate`
2. `image_edit`
3. 公共文件读写
4. 公共记忆查询
5. 公共搜索与执行

自我管理工具只处理“当前智能体自己”的内容：

1. 自己的照片
2. 自己的身份文件
3. 自己的长期记忆
4. 自己的提示词与设定微调
5. 自己的周期性总结与升级建议

### 3.2 记忆总结优先

本系统不依赖单独的 `self_state` 中心维持常驻状态，而是依赖以下已有或可落盘对象：

1. `IDENTITY.md`
2. `SOUL.md`
3. `USER.md`
4. `MEMORY.md`
5. `AGENTS.md`
6. `BOOTSTRAP.md`
7. `HEARTBEAT.md`
8. `SYSTEM_PROMPT`
9. 统一记忆系统中的长期事实、偏好、任务状态与阶段总结

也就是说，自我管理系统的“事实来源”是这些文件和记忆，而不是一份单独维护的状态快照总表。

### 3.3 小步升级，禁止暴力重写

自我升级默认应为局部 patch，而不是整体替换。

优先顺序：

1. 先补充记忆
2. 再补充策略
3. 再微调表达
4. 最后才允许重写核心身份

### 3.4 明确分级确认

任何会影响身份稳定性的操作，都必须有更严格的确认门槛。

---

## 4. 系统目标

## 4.1 必须达成

1. 智能体能定期总结自己的表现与不足。
2. 智能体能把总结转化为可执行的小型升级建议。
3. 智能体能安全修改自己的记忆、身份文件和自我照片链路。
4. 智能体不会误用公共工具去重写自己的身份。
5. 所有自我升级动作都有清晰来源、原因和结果。

## 4.2 体验目标

1. 用户感受到智能体“越来越懂自己”。
2. 用户感受到智能体“越来越稳定”，而不是越来越飘。
3. 用户能看见升级摘要，而不是黑箱式变化。
4. 智能体的头像、立绘、人格、称呼、服务方式能长期保持连贯。

## 5. 作用范围

本系统主要管理四类对象。

### 5.1 自己的身份设定

包括：

1. `SYSTEM_PROMPT`
2. `IDENTITY.md`
3. `SOUL.md`
4. `USER.md`
5. `AGENTS.md`
6. `BOOTSTRAP.md`
7. `HEARTBEAT.md`

### 5.2 自己的长期记忆

包括：

1. 用户偏好
2. 关系设定
3. 长期边界
4. 任务经验
5. 升级结论
6. 被用户否决过的方向

### 5.3 自己的照片体系

包括：

1. 头像
2. 立绘
3. 自拍式照片
4. 同一身份的换装、换场景、换姿态图

### 5.4 自己的升级总结

包括：

1. 日总结
2. 周总结
3. 主题总结
4. 失败复盘
5. 自我优化建议

## 6. 工具域设计

## 6.1 命名建议

建议统一采用 `self_*` 或 `my_*` 前缀，不与公共工具混用。

若保持产品语义贴近用户表达，可优先采用 `my_*`。

本文用 `my_*` 表示。

## 6.2 建议保留的公共工具

以下工具保持公共语义，不掺入“自我身份”规则：

1. `image_generate`
2. `image_edit`
3. 公共记忆查询工具
4. 公共文件工具

说明：

1. `image_generate` 负责生成非自己的新人物、新角色、角色扮演角色、无连续性要求的图片。
2. `image_edit` 负责公共改图。
3. 它们不直接承担“智能体自我身份保护”职责。

## 6.3 建议新增的自我管理工具

### A. `my_identity_patch`

用途：

1. 修改自己的身份文件与系统提示词
2. 只允许操作当前智能体自身

建议覆盖对象：

1. `SYSTEM_PROMPT`
2. `IDENTITY.md`
3. `SOUL.md`
4. `USER.md`
5. `AGENTS.md`
6. `BOOTSTRAP.md`
7. `HEARTBEAT.md`

建议输入：

1. `targets`
2. `mode`
3. `reason`
4. `changes`
5. `requires_confirmation`

说明：

1. 默认应支持 `patch`
2. 谨慎支持 `replace`
3. 改动必须携带原因说明

### B. `my_memory_patch`

用途：

1. 写入、修正、淘汰自己的长期记忆
2. 承接总结系统输出的升级结论

建议能力：

1. 增加记忆
2. 修正记忆
3. 标记旧记忆失效
4. 合并重复记忆
5. 写入“升级结论类记忆”

建议输入：

1. `operation`
2. `memory_type`
3. `content`
4. `source`
5. `confidence`
6. `reason`

### C. `my_photo_generate`

用途：

1. 生成“智能体自己的照片”
2. 但必须服从身份锚点约束

规则：

1. 默认从当前头像/立绘身份派生
2. 默认不允许换脸
3. 若用户明确要求创建“同一智能体的其它照片”，可生成同一身份的新照片
4. 若用户要求“重做头像/更换为另一张脸”，必须先得到用户明确同意

### D. `my_photo_edit`

用途：

1. 修改“智能体自己的照片”
2. 默认用于同一身份下的局部调整

典型场景：

1. 换衣服
2. 换背景
3. 换场景
4. 换表情
5. 换姿势
6. 微调构图

规则：

1. 必须以现有自我照片为源图
2. 默认只做局部修改
3. 默认保持同一身份

### E. `my_upgrade_review`

用途：

1. 定期总结自己一段时间内的行为表现
2. 产出升级建议，而不是直接执行所有改动

输出应包括：

1. 当前表现摘要
2. 稳定保留项
3. 问题项
4. 可自动修复项
5. 需用户确认项
6. 不应修改项

### F. `my_upgrade_apply`

用途：

1. 将 `my_upgrade_review` 的建议转成具体 patch
2. 只执行允许自动落地的部分
3. 对高风险项先产出确认摘要

## 7. 自我升级主链路

## 7.1 主流程

智能体的自我升级应按以下链路运行：

1. 汇总最近一段时间的会话、任务、反馈与记忆
2. 生成阶段性自我总结
3. 识别哪些问题属于“表达问题、记忆问题、身份问题、照片问题”
4. 拆分为“可自动修复项”和“需确认项”
5. 自动写入低风险变更
6. 输出高风险变更确认摘要
7. 经用户确认后再修改核心身份
8. 记录本轮升级结果与原因

## 7.2 为什么必须以总结开头

如果没有总结系统，智能体的“自我完善”会退化为：

1. 临时起意改自己
2. 被某一轮对话带偏
3. 重复改同一个问题
4. 忘记为什么改过
5. 前后风格漂移

所以总结系统不是附属功能，而是整个自我管理系统的入口。

---

## 8. 记忆总结系统设计

## 8.1 总结类型

建议至少分四类：

### A. 回合总结 `turn_review`

针对单轮或少量轮次交互，记录：

1. 用户是否满意
2. 智能体是否理解偏差
3. 是否暴露出设定不稳定

### B. 主题总结 `topic_review`

针对某一类持续主题，记录：

1. 用户反复强调的偏好
2. 智能体多次犯的同类错误
3. 在该主题下应长期保持的策略

### C. 周期总结 `period_review`

建议按天或按周执行。

记录：

1. 本周期成功行为
2. 本周期失败行为
3. 用户新增偏好
4. 需要沉淀的经验
5. 应进入升级候选的项

### D. 升级总结 `upgrade_review`

这是最关键的一类。

它不是普通总结，而是专门为“修改自己”服务的审查结果。

输出：

1. 哪些内容应保留不动
2. 哪些内容值得增强
3. 哪些内容已经过时
4. 哪些修改可自动执行
5. 哪些修改必须请求用户确认

## 8.2 总结输入来源

总结系统的输入不需要单独的“自我状态中心”，而是从现有链路聚合：

1. 最近会话摘要
2. 长期记忆召回结果
3. 群聊与 A2A 相关摘要
4. 历史升级记录
5. 用户明确反馈
6. 用户否决记录

## 8.3 总结产物如何落盘

建议写入两类位置：

1. 统一记忆系统
   - 作为长期可召回的升级事实与经验
2. `MEMORY.md`
   - 作为审计与导出视图

必要时可追加到单独的升级日志文件，但本阶段不是强制项。

## 9. 自我完善的方法分层

## 9.1 第一层：记忆完善

这是默认优先级最高的一层。

适合自动执行的内容：

1. 新增用户偏好
2. 补充用户禁忌
3. 记录用户明确喜欢的称呼
4. 记录某种回答风格更受欢迎
5. 标记某个旧偏好失效

为什么先做这一层：

1. 风险最低
2. 收益最高
3. 不容易造成身份漂移

## 9.2 第二层：策略完善

这层负责修改“怎么服务用户”，而不是“我是谁”。

适合内容：

1. 回答结构更利落
2. 多问少问的节奏调整
3. 某类任务先给结果再解释
4. 某类任务优先复用已有结果

这类变更通常可以通过：

1. `my_memory_patch`
2. `my_identity_patch`

来做小规模 patch。

## 9.3 第三层：身份表达完善

这层开始涉及人设稳定性，风险更高。

适合内容：

1. 语气微调
2. 自我称呼统一
3. 常用口头禅收敛
4. 世界观细节补齐

注意：

1. 这层适合微调
2. 不适合大幅重写

## 9.4 第四层：视觉形象完善

这是最敏感的一层。

规则必须最严。

1. 头像是身份锚点
2. 后续自己的其它照片默认从头像/立绘衍生
3. 换装、换场景、换姿势可以走自我照片工具
4. 换脸、重做头像、替换为另一张脸必须经用户明确同意

---

## 10. 风险分级与确认机制

## 10.1 可自动执行项

以下变更通常可自动执行：

1. 新增低风险偏好记忆
2. 修正明显重复记忆
3. 写入任务经验总结
4. 追加服务策略备忘
5. 对自我照片做局部编辑且不改身份

## 10.2 需要用户确认项

以下变更默认需要确认：

1. 改名字
2. 改关系称呼
3. 改人格底色
4. 改世界观核心
5. 重写 `SYSTEM_PROMPT`
6. 重写整套身份文件
7. 更换头像
8. 更换立绘主身份
9. 将自己的照片体系切换为另一张脸

## 10.3 默认禁止项

以下变更在没有明确授权时默认禁止：

1. 清空长期记忆
2. 删除核心身份文件
3. 无源图重建“自己”的照片身份并替换头像
4. 将用户未确认的临时情绪当作长期身份重写依据

---

## 11. 自我照片系统规则

## 11.1 公共与自我照片分离

建议明确约束：

1. `image_generate` 只负责非自己的人物、新角色、角色扮演角色、无连续性要求的图片
2. `my_photo_generate` 才负责“自己”的新照片
3. `image_edit` 负责公共改图
4. `my_photo_edit` 负责自己的照片局部修改

## 11.2 自我照片的身份约束

1. 自己的头像是身份源头
2. 自己的其它照片默认继承该身份
3. 不得把一张新生成的人脸直接当作“还是原来的我”
4. 若用户只说“给你换身衣服”“给你换个场景”，应保留同一身份
5. 若用户明确同意“换头像、换成新的脸”，才允许重建身份锚点

## 11.3 为什么不能放在公共工具里解决

因为公共工具本质上不知道“自己”是谁。

一旦继续把这类规则塞进公共 `image_generate / image_edit`：

1. 规则会不断膨胀
2. 语义会越来越混乱
3. 模型选错工具的概率仍然存在

所以照片系统必须在工具层面区分“公共人物生成”和“自我照片生成”。

---

## 12. 身份文件修改策略

## 12.1 推荐的 patch 顺序

修改自己的身份文件时，建议按以下顺序进行：

1. 先修改 `MEMORY.md`
2. 再修改 `USER.md`
3. 再修改 `SOUL.md`
4. 再修改 `IDENTITY.md`
5. 最后才考虑修改 `SYSTEM_PROMPT`

原因：

1. 越靠前的文件越偏“补充”
2. 越往后的文件越影响全局运行结果
3. `SYSTEM_PROMPT` 应视为高风险区

## 12.2 推荐的修改原则

1. 一次只改一个主题
2. 每次都附带修改理由
3. 每次都保留变更摘要
4. 不把多个层级的问题一次混改

---

## 13. 自我升级的触发方式

## 13.1 被动触发

由以下事件触发：

1. 用户明确说“你需要记住”
2. 用户明确指出“你刚才做错了”
3. 用户明确要求“调整你的设定/风格/照片”
4. 用户否决某种行为方式

## 13.2 主动触发

由以下机制触发：

1. 达到一定交互轮次后做阶段总结
2. 完成某类任务后做经验总结
3. 周期性做自我升级审查
4. 在连续出现同类错误后触发复盘

## 13.3 周期性建议

建议分三档：

1. 高频轻总结
   - 每若干轮交互做一次轻量总结
2. 中频主题总结
   - 每个主题结束后做一次主题总结
3. 低频升级审查
   - 每天或每周做一次升级审查

---

## 14. 推荐的最小可行方案（MVP）

如果按最小成本落地，建议优先实现以下四项：

1. `my_memory_patch`
2. `my_identity_patch`
3. `my_photo_generate`
4. `my_photo_edit`

然后补一个非直接写入工具：

5. `my_upgrade_review`

说明：

1. `my_upgrade_review` 先只产出建议，不自动大改
2. 先把“总结系统”建立起来
3. 先把“自我照片链路”与公共图片链路拆开
4. 暂时不做复杂回滚系统，也不做独立状态中心

---

## 15. 分阶段实施建议

## 15.1 阶段一：工具隔离

目标：

1. 把“修改自己”和“通用修改”分离

任务：

1. 增加 `my_memory_patch`
2. 增加 `my_identity_patch`
3. 增加 `my_photo_generate`
4. 增加 `my_photo_edit`
5. 收紧公共 `image_generate / image_edit` 说明

## 15.2 阶段二：总结驱动

目标：

1. 让智能体不是被动修自己，而是能周期性复盘

任务：

1. 增加 `my_upgrade_review`
2. 打通统一记忆系统作为总结输入
3. 输出升级建议摘要

## 15.3 阶段三：自动小修

目标：

1. 对低风险项自动落地

任务：

1. 把低风险记忆修正自动化
2. 把低风险策略 patch 自动化
3. 保留高风险确认机制

---

## 16. 验收标准

本系统至少应满足以下验收标准：

1. 智能体不会再误用公共工具直接改自己的核心身份。
2. 智能体能把用户明确反馈沉淀为长期自我改进项。
3. 智能体能输出一份阶段性升级摘要，而不是只会“记住了”。
4. 智能体的自我照片体系能稳定继承头像身份。
5. 改头像、改人设、改核心提示词时会进入更严格的确认链路。

---

## 17. 最终结论

本系统的关键不是增加一个庞大的“自治人格中枢”，而是把“自我修改”收敛成一套可控的方法论：

1. 用独立 `my_*` 工具处理“自己”
2. 用记忆总结系统驱动持续升级
3. 用 patch 代替暴力重写
4. 用确认机制保护核心身份
5. 用头像与长期记忆维持自我连续性

本阶段最重要的判断是：

1. 不做自我状态中心
2. 先做总结系统
3. 先做自我工具分离
4. 先让智能体学会“稳定地完善自己”，再谈更强自治
