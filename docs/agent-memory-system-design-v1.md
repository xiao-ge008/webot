# 智能体记忆系统详细设计方案（OpenFang 主架构增强版）

日期：2026-03-10  
状态：Draft v1  
适用范围：`weBot-app` + `openfang` 联合部署  
设计目标：在不引入外部重型记忆中间件的前提下，实现“智能总结 + 长期高质量快速召回”。

---

## 1. 背景与结论

### 1.1 当前结论

1. 以 OpenFang 记忆系统作为主记忆底座是正确路线。  
2. `workspace/memory/*.md` 不应再承担主召回职责，应降级为审计/人工可读备份层。  
3. 不做 MemOS / EverMemOS 整体接入，避免高重复建设与跨服务时延放大。  
4. 在 OpenFang 源码层做“最小侵入增强”，补齐记忆编排与治理能力。

### 1.2 当前主要痛点

1. 记忆双轨并存但无统一编排，召回口径不一致。  
2. 记忆写入粗粒度，噪声高、重复多。  
3. 缺记忆类型化管理，无法针对性治理 TTL / 权重 / 冲突。  
4. 检索路径偏单一，召回稳定性不足。  
5. 缺反馈纠错和可解释性闭环。

---

## 2. 设计目标与非目标

## 2.1 目标（必须达成）

1. 智能体可自动完成多层总结：`turn -> topic -> episode`。  
2. 长期记忆召回稳定且快：本地部署场景下 P95 召回延迟控制在 120ms 以内（不含大模型生成时间）。  
3. 记忆具备可治理能力：去重、冲突检测、版本关系、可撤销。  
4. 统一记忆编排：所有写入与召回通过同一策略入口完成。  
5. 强可观测：指标、日志、审计链路完整。

## 2.2 非目标（当前阶段不做）

1. 不引入外部多数据库重型栈（如 Mongo + ES + Milvus + Redis 全家桶）。  
2. 不做跨产品级全局共享记忆网络。  
3. 不在 P0 阶段追求复杂自我进化策略（先保证稳定和可控）。

---

## 3. 总体架构（分层 + 编排）

## 3.1 记忆分层模型

1. L0 工作记忆（Working Memory）  
用途：当前请求上下文拼装与即时推理。  
特点：生命周期最短，不持久化或低价值持久化。

2. L1 会话记忆（Session Memory）  
用途：同一会话近期轮次连续性。  
特点：保留原始对话 + turn summary。

3. L2 长期语义记忆（Semantic Long-Term）  
用途：跨会话的事实、偏好、长期任务信息。  
特点：向量 + 关键词混合检索，长期存储。

4. L3 结构关系记忆（Knowledge/Preference/Tool）  
用途：实体关系、用户偏好演化、工具调用经验。  
特点：支持关系查询与冲突决议。

5. L4 归档审计层（File Archive）  
用途：`MEMORY.md` 与 `memory/*.md` 人工可读审计、导入导出。  
特点：默认不参与主召回，仅在诊断/回放时使用。

## 3.2 统一记忆编排器（Memory Orchestrator）

统一入口职责：

1. 写入侧：抽取、分类、评分、去重、冲突处理、异步索引。  
2. 读取侧：意图路由、混合召回、统一重排、上下文打包。  
3. 治理侧：TTL、衰减、归档、撤销、审计追踪。

---

## 4. 数据模型设计（逻辑层）

## 4.1 记忆主实体 `memory_item`

核心字段建议：

1. 标识维度：`id`, `agent_id`, `tenant_id`, `user_id`, `session_id`  
2. 语义维度：`type`, `text`, `content_json`, `embedding`  
3. 质量维度：`importance`, `confidence`, `source`, `evidence_refs`  
4. 生命周期：`created_at`, `updated_at`, `expires_at`, `status`  
5. 版本关系：`version`, `supersedes_id`, `conflict_group_id`  
6. 安全维度：`namespace`, `pii_level`, `visibility`

`type` 建议枚举：

1. `fact`：稳定事实。  
2. `preference`：用户偏好。  
3. `task_state`：任务进度、约束、TODO。  
4. `tool_experience`：工具调用经验与失败模式。  
5. `summary_turn` / `summary_topic` / `summary_episode`：分层摘要。  
6. `policy`：长期规则与禁忌（如风格约束）。

## 4.2 证据与反馈实体

1. `memory_evidence`：摘要/结论与原始消息 ID 的映射。  
2. `memory_feedback`：用户反馈（正确/错误/过时/删除请求）。  
3. `memory_access_log`：召回解释日志（为何命中、得分构成）。

## 5. 写入策略设计（智能总结核心）

## 5.1 每轮写入流水线

1. 候选抽取  
从用户输入、助手输出、工具结果中抽取候选记忆片段。

2. 类型判定  
按 `fact/preference/task_state/tool_experience` 分类，避免“整段对话直接入库”。

3. 重要性评分  
计算 `importance`（例如 0-1）：用户明确要求、可复用价值、长期相关度越高分越高。

4. 去重  
文本近似 + 向量近似 + 键位规则（同实体同属性）联合去重。

5. 冲突检测  
当同一事实槽位出现新值，建立 `supersedes` 关系而非硬覆盖。

6. 同步/异步分流  
高价值记忆（`preference`, `task_state`）同步写；低价值记忆异步批写。

## 5.2 分层总结策略

1. `turn summary`（每轮）  
提炼本轮核心事实/决策/约束，字数短，必须附证据指针。

2. `topic summary`（每 8-12 轮或主题切换）  
聚合当前主题内有效结论，更新主题级上下文。

3. `episode summary`（任务结束或日终）  
沉淀可长期复用知识，保留可逆追溯链。

4. 可逆原则  
所有 summary 必须可回溯到 source messages，避免不可逆信息损失。

---

## 6. 召回策略设计（长期高速召回核心）

## 6.1 召回总流程

1. 意图识别路由  
识别当前问题偏向：事实查询、偏好延续、任务续作、工具排错。

2. 多路候选召回  
同时执行：
- FTS 关键词召回（快）  
- 向量召回（语义）  
- 关系召回（实体/偏好/工具经验）

3. 融合重排  
统一评分后输出 TopN：

`final_score = a*semantic + b*lexical + c*recency + d*importance + e*confidence - f*conflict_penalty`

4. 上下文预算分配  
按类型配额打包，例如：`fact 40% + task_state 30% + preference 20% + tool_experience 10%`。

5. 安全过滤  
剔除 `expired/revoked/conflicted-loser` 记忆，避免旧错信息回流。

## 6.2 性能策略

1. 热层缓存  
缓存最近命中的高频记忆与 embedding。  

2. 预计算  
写入时异步完成 embedding 与索引，不阻塞主响应。  

3. 动态 TopK  
按问题复杂度动态调整召回深度，简单问题走浅召回。  

4. 降级路径  
向量检索异常时自动降级到 FTS + recency，保证可用性。

## 7. 记忆治理与安全

## 7.1 命名空间策略

1. `self.*`：仅 agent 私有记忆。  
2. `shared.*`：授权共享记忆，需显式写权限。  
3. `tenant.*`：租户级隔离记忆。  
4. `system.*`：系统策略记忆（只读或受限写）。

## 7.2 生命周期治理

1. TTL 策略按类型配置：  
- `task_state` 可短 TTL  
- `preference` 长 TTL  
- `fact` 依据置信度和反馈动态更新

2. 衰减机制  
长时间未命中且低重要性记忆降权，不立即删除。

3. 删除与撤销  
支持软删除 + 审计日志；召回链路默认忽略撤销项。

## 7.3 隐私与合规

1. 标注 `pii_level`（none/low/high）。  
2. 高敏信息默认不进长期层或仅加密持久化。  
3. 审计接口可追踪“何时由谁写入/修改/召回”。

---

## 8. 可观测与评测体系

## 8.1 在线指标（运行期）

1. 召回质量：Recall@K、MRR、误召回率。  
2. 记忆健康：去重率、冲突率、过期命中率。  
3. 性能：P50/P95 召回延迟、索引延迟、每轮记忆开销。  
4. 体验：用户“连续性”评分（是否记得我、是否记得对）。

## 8.2 离线评测（发布前）

1. 构建标准任务集：事实延续、偏好延续、长期任务续作、纠错回归。  
2. 每次策略变更跑回归评分，设置发布门槛。  
3. 关键门槛示例：  
- Recall@5 不低于基线 +10%  
- 冲突误用率低于 2%  
- P95 召回延迟不超过目标阈值

---

## 9. 迁移与落地路线图

## 9.1 P0（1-2 周）：统一读路径

1. 建立 Memory Orchestrator 读入口。  
2. 主召回来源统一到 OpenFang 结构化层。  
3. `memory/*.md` 仅作旁路回放，不参与默认主召回。

交付标准：召回结果可解释，延迟可观测。

## 9.2 P1（2-3 周）：智能写入与分层总结

1. 上线写入抽取、分类、评分、去重、冲突处理。  
2. 上线 `turn/topic/episode` 三层总结。  
3. 完成历史 `memory/*.md` 回灌（`source=file_archive`）。

交付标准：记忆噪声显著下降，跨会话连续性提升。

## 9.3 P2（2-4 周）：治理闭环与质量优化

1. 上线反馈纠错与版本关系。  
2. 上线动态重排与类型预算。  
3. 持续调参与 A/B 验证。

交付标准：可持续优化机制建立完成。

## 11. 风险与回滚

## 11.1 主要风险

1. 记忆写入策略过严导致信息漏记。  
2. 冲突规则错误导致新旧事实误替换。  
3. 混合检索权重不稳导致召回波动。

## 11.2 回滚策略

1. 保留旧召回路径开关（feature flag）。  
2. 总结写入与冲突处理可独立关闭。  
3. 文件归档层持续保留，确保可回放与数据恢复。

---

## 12. 最终决策建议

1. 架构路线：`OpenFang 主记忆 + 本地增强编排 + 文件层审计归档`。  
2. 产品策略：优先提升“记得对、记得稳、召回快”，再追求复杂自学习。  
3. 工程策略：先统一编排，再逐步做模型化优化，避免一次性大重构失败。
